# 茶馆情报、意外事件与分支任务线更新计划

日期：2026-09-13。本文将本轮讨论整理为产品设计、实施与验收计划。核心方向来自用户讨论；内容数量、费用、触发概率和经济门槛属于本计划的首版实施取值，可根据试玩结果调整。本文不代替完成报告；实际验证结果以根目录 `TEST_REPORT.md` 中对应更新的记录为准。

目标体验：玩家在经营途中遇到必须回应的意外，当场作出有取舍的决定；回到茶馆后看见事情继续发展，并通过真实经营行动改变人物的命运与自己的生意。

实施状态：本轮实现与验收已完成（2026-09-13）。证据与局限见[茶馆更新验收](../../TEST_REPORT.md#茶馆情报意外事件与分支任务线--2026-09-13)。按用户要求纳入本地主分支提交；未推送或发布。

## 1. 已确认的产品方向

1. 意外发现使用强制弹窗，必须当场回应，保持意外性和紧迫感。
2. 现场只处理眼前的事，后续信件、调查、承诺和结局进入情报系统。
3. 采用多阶段任务线：从具体人物和局部矛盾展开，逐步认识相关人物，发现新问题并作出选择。
4. 不同选择必须改变后续剧情、人物、目标或结局，不能只换文案和奖励数值。
5. 故事影响真实经营，包括库存交付、生产、现金、手艺经验、人物合作和有限货源。
6. 保留连续时间、宋风纸本淡彩、真实反馈和当前存档唯一支持边界。

任务线结构借鉴连续叙事的体验，全部人物情节采用汴梁原创内容。不引入战斗、装备品质、任务经验等级或新的通用货币。

## 2. 当前问题与替换边界

旧版普通见闻虽然有120条语义模板，主要流程却相同：听消息、追问、等待、回访，再按统一概率显示办成或落空。题材去重不能解决操作重复，普通见闻也没有经营后果。

旧随机遭遇已有资源和人物效果，但采用整页替换、统一查问费用和分散的后续队列。此次复用现有库存、时间、账本、订单与人物规则，替换其故事组织方式。

- 删除无实际作用的普通见闻模板、统一兑现抽签和旧人物后续队列。
- 保留实际世界事件驱动的行情线索。
- 现有订单、生产、交易、住宅和熟客系统继续提供实际经营操作，不复制第二套同类规则。
- 场景随机性决定遇到谁和发生什么；已经作出的明确选择不能被随机抽签改写。

## 3. 发现渠道与强制弹窗

| 渠道 | 主要内容 | 呈现 |
| --- | --- | --- |
| 实际外出经营 | 现场冲突、求助、临时机会 | 强制弹窗 |
| 茶馆主动打听 | 新故事、行情和远处机会 | 情报页线索 |
| 熟人来信 | 此前行为引出的后续 | 更新原故事，不再收茶钱 |

同一故事只有一个实例，多渠道发现补充原进度，不能重复开场或领奖。

### 3.1 弹窗交互

流程：原经营操作完整结算并保留反馈 → 强制现场弹窗 → 调查或选择 → 结算现场 → 恢复原经营界面 → 后续进入故事。

- 弹窗覆盖当前场景，背景保持可见，不再替换整个工作区。
- 标题、人物、经过、已知线索、具体回应和成本按固定阅读顺序排布。
- 遮罩、Escape和背景导航不能绕过；焦点限制在弹窗内，结束后恢复原交互位置。
- 必须有零现金、零体力可执行的拒绝或离开选项；拒绝默认不消耗时间。
- 强制回应不等于强制接任务，明确接受后才产生承诺。
- 阅读不推进游戏时间，不设置现实秒数倒计时。紧迫感来自眼前局面、行动耗时、截止时刻和后果。
- 查问内容、费用与耗时按场景配置，已知证据不能重复付费获取。
- 单个现场可直接结束，也可开启长线；不能把现场留在路边数日再处理。
- 刷新恢复同一个现场和查问状态，不重抽。
- 页面与WebMCP使用相同的阻塞规则，不能借接口绕过现场回应。

### 3.2 触发节奏

首日不随机触发；每生活周期最多一次随机现场。沿用现有42%抽取基线，同时按实际操作场景筛选。

- 交易、搬运与外出劳动分别匹配可发生的现场。
- 导航、打开详情和居家操作不抽取无关街头事件。
- 原操作完成后至多弹一个现场，回应现场不继续连锁抽取。
- 同家族至少冷却七个游戏日，非重复故事本局只开场一次。
- 普通来信不占随机遭遇机会；任务后续只在确有新现场的情境下才再次弹窗。

## 4. 首批内容与分支要求

首批为16个独立现场和6条完整故事线，6个现场同时承担故事线开场，其余10个可短篇收束。

每条主要路线包含4—6个叙事节点（包括开场与结局），至少两条不同中段路线、两个独立结局、三种参与方式。允许有调查、补救和回头选择，不限制为一棵不可交汇的树。

### 4.1 六条故事线

| 故事线 | 主矛盾 | 分支与实际影响 |
| --- | --- | --- |
| 一篮碎蛋与一纸欠账 | 摊主、食肆与脚夫的数量争议 | 垫货供货／核账／查证运输，分别通向卖蛋熟客或摆渡人合作；超时可事后核账 |
| 戏班开演之前 | 开演期限与衣箱损坏 | 采购新布／自己织布／修补旧衣，通向供货关系或纺织经验；误期后归还借衣 |
| 粮埠换主 | 新旧掌柜的货物归属 | 核验封条与仓簿／独立向磨坊供粮，获得有限新仓货源或认识行商、饼铺 |
| 绣坊师徒 | 旧订单交期与徒弟的新样 | 稳住旧单／支持独立试样，改变人物立场，获得商路或实际纺织经验 |
| 旧屋檐下 | 两户漏水、备料与维护责任 | 备料生意／清沟调查／协调维护，通向有限柴料机会或街坊与客栈往来 |
| 外乡厨客的一席饭 | 家乡原味与本地口味 | 支持原方试作／调整地方口味并配食，形成不同菜谱结局、食品经验或供货关系 |

### 4.2 十个独立短事件

钱袋认主、短布辨验、断绳货车、订席单误会、雨棚抢救、药签核对、秤盘争执、错址家书、灯架重扎和船铃认主。

短事件分别涉及证据判断、时间体力取舍、协调、劳动和人情；不以换人物名算新的事件。不再维护“普通吃饭”“普通住宿”“普通治疗”的另一套遭遇规则。

### 4.3 有效分支的判定

不同选择必须改变后续人物、问题、证据、行动、承诺或结局中的至少一项。单纯奖励数量差别不算剧情分支。

分支可以交汇，但此前的选择、已知证据与人物态度必须保留。比如从帮陈婆婆垫款进入欠账线，从护送阿成进入运输查证线；最后都能对账，但此前经历和合作对象不同。

失败、错过和放弃分别处理：未接受就拒绝不算违约；已承诺但超时，原报酬失效并进入专门的补救或收束；主动放下故事结束当前承诺，本局不重新领取同一任务。

每个阶段配置必须齐备：开启条件、正文、已知目标、成本、行动、下一节点、奖励、等待/截止条件及结局。交付前清楚说明保证报酬和未承诺的答谢，禁止占位剧情和统一“办妥”结尾。

## 5. 茶馆与故事工作区

### 5.1 听茶

保留8文、30分钟、每生活周期一次。关注方向为随意听听、买卖、手艺、街坊，影响抽取倾向，不保证指定奖励。

每次1—2条新线索。无新内容时，不扣钱、不耗时、不消耗当日机会。已有故事的正常来信自动更新，不能再次收费或占新线索名额。

行情保留实际世界事件；公开动静出现或所传时限过去后直接更新结果，不要求逐条专程回访。未公开时可主动追问证据，不能预告隐藏真相。

### 5.2 列表与详情

列表按故事聚合，提供全部、可推进、等待后续、已结束、行情线索筛选。显示故事名、当前章节、状态与新进展，不将每次来信拆成重复条目。

详情依次展示当前正文、目标和承诺、时限、可执行行动、可展开历史。历史保留玩家实际选择和后果；未发现章节、未走分支与隐藏结局不展示。

- 交付和限量货源在市场的故事交付区执行，带着当前故事跳转。
- 自己织布路线提供生产入口，只在实际生产完成时累计阶段进度；采购和旧库存不冒充本次生产。
- 调查和协商在故事详情执行，但费用、条件与结果由共享引擎控制。
- 等待状态显示已知到期时刻，来信前不提前展示下一阶段正文。
- 同时最多主动承担3条故事线；等待中的已接受故事计入，未接受线索不计入。
- 已有任务的更新不受上限影响，放弃需要明确说明后果。
- 今日要事仅提示当前可推进/限时故事并跳转，完整剧情仍在情报页。

## 6. 共享引擎、公开接口与持久化

### 6.1 状态与数据流

事件定义与玩家实例分离。实例保存发现渠道、当前阶段、状态、可用时刻、截止时刻、已知证据、生产进度、选择历史和有限机会。

统一管理唯一待回应现场与最多3条活动故事，移除旧人物后续队列。活动任务不受近期消息截断影响。人物变化关联实际合作或手艺，不增设无用途的好感度数字。

行动携带实例ID、阶段ID、行动ID，并沿用全局revision防重复提交。陈旧阶段、未知选择、资源不足和非法时段全部回退，不扣资源、不推进时钟。

### 6.2 经营与账目

- 实际交付才扣库存并推进目标，持有货物或卖给其他人不算交付。
- 交付按共享搬运规则计算时间和体力，限量采购使用同一运输报价及仓储校验。
- 原料与成品保留原成本；货款按贸易/生产收入及对应成本记账，捐赠和试作投入记实际库存耗用。
- 劳动报酬、采购和货物毛利分别入账，不将奖励虚构成销售利润。
- 合作货源有限量和有效期，购足或到期结束，不叠加永久折扣。
- 阶段奖励只结算一次，即使回到旧分支也不能刷经验、现金或机会。
- 当前阶段生产目标从真实生产完成入库累计，不根据库存总量倒推。
- 完成时刻等于截止视为准时；超过截止进入对应后续，旧奖励失效。
- 长等待和收工预览提示将跨越的故事承诺，供玩家先处理。
- 离线与阅读不推进时间。

### 6.3 WebMCP

公开已发现故事的章节、已知正文、目标、历史、可执行选项及实际预览；现场公开已知线索与已取得的证据。

新增故事选择、阅读、放弃和有限货源采购操作。禁止直接序列化完整内容定义、未来节点、隐藏证据或后续奖励。

现场未回应时，接口同样拒绝无关经营操作。公开结果与界面共享计算，避免两套状态说明。

### 6.4 存档

保留 `bianliang-save-v4` 键，`saveRevision` 从4升至5。旧修订需要重新开始，不迁移、不回填人物经历、不生成修复备份。

新存档必须包含完整故事状态和当前现场。拒绝未知故事/阶段、重复实例、缺少必要字段、非法期限和不匹配的现场数据。普通刷新保留当前分支、查问状态和奖励结算，不重新抽取。

## 8. 验证与完成标准

除技术正确性外，必须回答三个体验问题：玩家是否记得具体人物与自己的选择；后续是否让玩家改变一次真实经营安排；再次遇到事件时是否仍需要判断，而非机械点击同一个最优按钮。人工试玩记录具体例子和反例，作为调整依据。

### 8.1 规则与接口

验证所有内容图的节点可达、每个主要分支与结局、每个限时阶段的超时后续、低资源退出、技能替代路径、生产真实性、多渠道去重、三任务上限、回到旧阶段不重复奖励。

验证精确截止、跨午夜来信、陈旧请求、存读档往返、格式边界及隐藏信息。基础规则测试继续保留并迁移旧遭遇/见闻断言，不删除测试来掩盖行为变化。

运行 `npm run typecheck`、`npm run lint`、`npm test`、`npm run build`。

### 8.2 真实浏览器

至少1536×864、1920×1080、390×844，检查满列表、长正文、多选项、缺料禁用、历史展开、三任务并行、等待/结束状态及完整交付。

专门验证：遮罩与Escape不能关闭、焦点在弹窗内、背景操作不可用、零资源可告辞、刷新恢复同一现场、原操作反馈不丢失、不同选择走出不同故事。目视复查截图，不能只看布局断言。

运行完整既有浏览器套件和新增 `tests/browser-stories.mjs`；产物留在 `tests/browser-output/stories/`。

### 8.3 内容抽样

`npm run test:content` 运行100日抽样并生成前20次听茶、前20次现场及六条故事线正文。检查新线索不重复、无内容不收费、题材与参与方式差异，人工审阅分支因果和真实后果。

强制抽取只用于提高内容审阅覆盖，报告必须注明，不将该频率当成实际游玩体验。

### 8.4 经济对照

- 原有 `npm run simulate`：7种策略各30种子、100日，保持原六项门槛，不放宽。
- `npm run simulate:stories`：同一混合经营策略、相同30种子、100日，对比不参与、每三日选择性参与、每日频繁参与。
- 对照使用玩家已知选项与成本，不读取隐藏分支来挑最优结局。
- 统计净资产、现金、健康、存活率、故事耗时、实际推进与结束数量；费用均来自真实结算。
- 参与组必须实际推进故事；中位增长不超过基线1.5倍或基线加1000文中的较大值；存活率不得比基线低超过20个百分点。
- 超出门槛必须诊断内容效果或策略行为，不事后放宽标准。

所有验收完成后，逐项填写最新报告，明确样本、通过范围与剩余局限，才将此计划标记完成。

## 9. 丰富度与疲劳控制

- 丰富度同时来自题材、参与动作和后果：辨认证据、协调争议、赶工生产、备货交付、人情取舍不能都退化为支付一笔钱。
- 选择先交代玩家能判断的取舍，例如现金、耗时、需交货物和已知期限；未知的是事情如何发展，不能隐藏本应知道的操作成本制造意外。
- 短事件可以当场结束，让玩家获得小故事与即时影响；长故事分阶段展开，避免每次弹窗都新增一串任务。
- 同一故事本局不重复开场；可重复短事件遵守冷却。有限内容耗尽后如实告知没有新消息，不用同义改写假装新内容。
- 强制弹窗服务于现场决策。普通来信和已知任务进展进入情报页，避免把全部故事更新都变成打断。
- 分支允许交汇，以控制内容维护量；交汇后仍保留此前选择的记录及实际人物关系，不抹平玩家经历。
- 首版六条故事是可扩展内容基础，不承诺无限叙事。后续新增故事也必须交付完整分支、实际经营后果和相应验证，不能仅增加消息条数。

## 10. 本轮范围之外

不引入战斗、独立任务等级、通用好感度刷取、无限程序生成剧情或现实时间倒计时。暂不要求跨多条故事的大型阵营主线；先确保每条短中篇故事本身完整、选择有效、结局可见，再考虑跨故事联动。
